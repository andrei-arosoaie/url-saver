Phase 7 · Article Connections

Connect what you save.

Shared entities + semantic similarity. Store connections across the owner’s entire library and show a Related articles section in article details.

Database diagramAll fieldsProcessing flow429 cooldownImplementation & tests
Approved: save first; process in the background; connections visible from both articles; recompute after relevant changes; backfill existing articles; skip URL/title-only records. Google gemini-embedding-001, server-side, free-tier-only. No paid fallback.

Database design

Seven new tables in existing Supabase PostgreSQL. Existing articles, entities and article_entities remain. This is a technical design draft, not an applied migration.

New article field: connection_revision BIGINT NOT NULL DEFAULT 0. Increment on content or entity-association changes. Keep the existing article version for client edit conflicts; use a text fingerprint to avoid paying or consuming quota again for unchanged text.

Constraints & indexes

  • Ownership: composite foreign keys enforce the same account for articles, embeddings, connections, evidence and jobs. Profiles and provider cooldowns are backend operational configuration, not user content.
  • Unique pair: UNIQUE(account_id, article_low_id, article_high_id), with article_low_id < article_high_id. No self-links; store A ↔ B once. Index each endpoint with account_id for Related articles retrieval.
  • Evidence: UNIQUE(connection_id, entity_id); verify that both endpoint articles still link to each shared entity. A connection may have shared-entity evidence, a semantic score, or both. Shared entity changes must not erase valid semantic evidence.
  • Embeddings: UNIQUE(account_id, article_id, profile_id, content_hash, chunk_index). No comparison between incompatible profiles. Validate finite values, expected dimensions and chunk boundaries. Hash scope and preprocessing must be deterministic.
  • Vector index: choose a fixed dimension and index strategy after model/profile review. Do not invent a vector(n) migration now. Account and current-content restrictions must apply to results; test indexed filtering returns enough owned candidates.
  • Jobs: UNIQUE(account_id, article_id, kind). Index eligible work by status/available_at and expired leases by lease_until. Coalesce updates, claim atomically with short row locks / SKIP LOCKED, and require lease_token on completion.
  • Cooldown: one row per real shared Gemini quota scope. Concurrent 429 handlers extend blocked_until atomically; never shorten an existing pause.
  • UTC: timestamps are TIMESTAMPTZ / Java Instant. Version/revision/count fields must be nonnegative. Query-derived connection counts are not extra article columns.

Approved removal policy: remove a connection only when successful current-revision recomputation finds no remaining reason. Do not remove links due to age, provider failure or pending processing. Never remove on partial semantic failure if the old semantic reason has not been successfully reevaluated. Preserve user pair exclusions. No article cascade policy is introduced by this draft.

Save → queue → connect

  1. One database transaction: save/update article or entity association, increment connection_revision when relevant, and upsert durable work. Rollback also rolls back queued work. Skip records without captured content.
  2. Return immediately: Gemini, vector search and connection creation are outside the save request.
  3. Claim work: the Spring Boot background worker claims an eligible job with a lease. Expired leases become eligible again after crashes/restarts. No transaction stays open during a network call.
  4. Embedding job: derive plain text without modifying stored HTML. Reuse compatible vectors with the same content hash; otherwise call gemini-embedding-001 and persist the result. Successful embedding generation schedules connection work.
  5. Connection job: find shared entities and query compatible current embeddings in pgvector. Shared-entity processing can continue while Gemini is paused; semantic processing waits for available embeddings.
  6. Publish safely: lock/recheck both endpoint revisions and content hashes before writing the canonical pair/evidence. Reject stale worker results and retain newer requested work. A title/category-only edit does not require new embeddings of unchanged body text.
  7. Read either side: Related articles selects pairs where the owned article is either endpoint, returns the opposite article and explicit reasons. Similarity scores are not factual proof or probabilities.

Process existing content-bearing articles through the same queue, in bounded batches with a resumable cursor. No Kafka, Redis, extra vector database or model-hosting service.

Google embedding generation

gemini-embedding-001 through the Gemini API, called only by Spring Boot. Mount credentials in secret YAML; never ship them to clients. Fill know.connections.embedding.gemini.api-key in server/config/embedding-secrets.yml (git-ignored); template: embedding-secrets.example.yml. Render secret filename: embedding-secrets.yml, imported from /etc/secrets/embedding-secrets.yml. Derive text from saved sanitized article HTML. All subsequent comparisons run in PostgreSQL/pgvector, orchestrated by Spring Boot.

Generate once per content/profile/chunk and reuse. Entity-association changes refresh connection evidence without regenerating unchanged text embeddings. Overlapping chunks are approved for long articles. Exact token size, overlap, aggregation and output dimensions require technical validation; never silently discard article text. Verify applicable provider data terms before enabling processing.

Gemini 429 → persistent cooldown

Pause all embedding requests sharing that quota. Initial cooldown: 24 hours, configurable in application.yml. Respect a longer valid Retry-After. Persist blocked_until in PostgreSQL, so restarts and multiple workers cannot bypass the pause.

Retain jobs as pending; do not repeatedly probe Gemini or consume the ordinary failure budget during the pause. Resume after cooldown; a new 429 extends it. Already in-flight calls may finish, but no new calls start after the pause is observed. A 24-hour backoff is not a guarantee of Google’s quota reset time.

Saving, reading, existing connections and shared-entity processing remain available. Show meaningful waiting/provider-limit status. No paid fallback. Other transient failures use five retries after delays of 1, 2, 4, 8 and 16 minutes. Delays and retry count are configurable; respect a longer valid Retry-After. After exhaustion, mark FAILED and expose a Retry action.

Manual connection removal

Provide a Remove connection action for each related article. Removing a connection affects the canonical pair, so it disappears from both articles. Keep both articles, their content, entity associations and completion history intact. Enforce owner checks.

All qualifying connections remain accessible. Do not impose a total cap of 10; paginate delivery when needed without discarding otherwise qualifying connections.

Approved: user-removed article pairs are excluded from all future automatic connection generation. Persist the exclusion across restarts, article updates, backfills and model changes. Removing A ↔ B does not exclude either article from connections with other articles.

Verify removal from either endpoint, visibility on both sides and cross-account isolation in unit/UI/full-flow integration tests.

Enforce manual removal

One transaction: insert the canonical pair exclusion, remove its shared-entity evidence and connection, and return success only after commit. Repeated removal is idempotent. Never delete either article or its entity links.

All connection generators, recomputation, backfill and model rebuilds exclude suppressed pairs. Recheck exclusions at publication and serialize removal/publication for the same pair, so an in-flight worker cannot recreate a removed connection. Existing retained embeddings may still serve other article pairs.

Required tests: remove from either side, verify absence on both, restart, article update, backfill, concurrent generation/removal and cross-account isolation. The removed pair stays excluded in every case.

Approved matching & progress verification

  • Use overlapping article chunks; select dimensions, token size and overlap through validation.
  • Connect above a configurable similarity threshold; calibrate its initial value with representative articles.
  • Remove automatically only after successful, current-revision reevaluation confirms no remaining reason; never override manual exclusions.
  • Retry transient non-429 failures with increasing configurable delays and an attempt ceiling, then mark failed. Permanent invalid requests are not retried as transient failures.
  • Poll backend progress while generation is pending; preserve existing links during updates.

Extension trigger → persistent backend state → webapp progress. The extension saves through the article API; the backend saves the article and queues work in the same transaction. On opening the article, the webapp reads the latest processing state and polls while pending. It does not depend on an extension-to-webapp message or the webapp having been open during saving. Backend jobs run independently of clients; closed UI does not prevent server-side processing.

Test UI opened after save and browser reload, cooldown/resume, failed jobs, updates during processing and user exclusions.

Use extension tests to verify real save-request/result handling and webapp tests to verify polling, status rendering and stopping at terminal state. Separately verify actual Firefox extension save → live backend/database → webapp progress/results on desktop and Android. API tests alone are not claimed as actual extension/device verification. Test provider failures without spending Gemini quota; a controlled live-provider smoke test is separate.

Related articles presentation

One chronological list of all qualifying related articles, newest added first. Use the related article’s saved_at timestamp (addition to the system), not connection creation or embedding time. Pagination must not impose a total result cap.

Label each article with its reasons: shared entities (show their names), semantic similarity, or both. A pair with both reasons appears once with both labels. Do not create separate article/entity result lists or sort primarily by semantic score.

Approved order: saved_at descending, then article UUID descending as the stable tie-breaker for equal timestamps. Match the timeline’s newest-first order.
