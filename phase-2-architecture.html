Identity, status & UTC years

TypeAllowed API statusesDefaultCompleted
BOOKTO_READ · READING · READTO_READREAD
MOVIE / TV_SHOWTO_BE_SEEN · SEENTO_BE_SEENSEEN
GAMETO_PLAY · PLAYING · FINISHEDTO_PLAYFINISHED
  • Exact duplicate: same owner, type and unmodified title. Dune, dune and titles with outer spaces are different. Blank titles rejected; no silent trimming.
  • Hash guard: application SHA-256 title digest, database verification, full-title comparison on conflict. This supports long titles without oversized text indexes.
  • Completion: actual transition into completed status or explicit Add completion appends an event and sets completed status atomically. Use supplied instant or server-now UTC automatically.
  • No-op: unchanged completed status does not append history. Repeated completion requires Add completion.
  • Year: [1 January 00:00:00Z, next 1 January 00:00:00Z). One entity row per year with its completion count; other years’ events remain.
  • History survives current status changes: a rereading/playing entity still appears in years with prior completion events. Year queries must not silently require the current completed status.
  • Unlink: delete one association. Keep entity, list membership, article, other links and every completion event.

Creation timestamps are server assigned. Completion timestamps are Java Instant / PostgreSQL timestamptz; responses serialize UTC. Relative timeline labels may display in viewer time, but history-year membership remains UTC.

Service structure

com.know.entities.presentation / application / infrastructure follows the existing feature/layer rules.

  • articles: capture, content, display classification/name, timeline search and owned article-reference lookup.
  • entities: entity commands/queries, exact-title identity, source associations, current status and completion events.
  • Cross-feature direction: entities calls an exposed articles application contract to verify owned source references. articles does not depend on entities. The webapp loads linked entities separately; no feature cycle.
  • Persistence: Flyway, explicit JPA queries, transactional write boundaries, infrastructure entities and MapStruct mappings. Application/presentation DTOs remain separate Java records.
  • Concurrency: version fields for entity/completion edits; database uniqueness for creates; transactionally serialize completion/status mutation. No automatic conflict overwrite.

Extensible categories · Phase 2

Categories are account-owned records, not a fixed enum. Seed Architecture, Development, AI, Other, Books, Movies, TV shows and Games with their current colors. Existing articles start in Other; new accounts receive the same defaults.

Store a stable key, display name, color, default/custom origin, enabled state, creation time and version. Articles reference the same owner’s category. Filters, editing choices and node colors read this catalog.

Phase 5: create personal categories, disable defaults and remove personal categories. Entity types and statuses remain separate.

Backend entity types

Java enum: BOOK · MOVIE · TV_SHOW · GAME. Persist enum names as strings, never ordinals. Categories remain data-driven records.

Approved consistency & pagination

Editing/deleting completion history preserves current status. Entity/completion writes use version checks; stale writes return 409. Exact-title uniqueness uses the SHA-256 guard.

Cursor pagination: default 20 / maximum 100. Both values are configurable in application.yml and mounted YAML overrides. Validate positive values and default ≤ maximum.

Approved defaults & search

Books: To read · Movies / TV shows: To be seen · Games: To play.
