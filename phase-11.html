Phase 11 · Movie integration

Movies, enriched.

TheTVDB supplies movie search and metadata. Know owns your movie, alias, status and completion history. The integration must support replacing the catalog provider.

ExperienceArchitectureDatabaseAPI contractsCache & reliabilityImplementation guide
Scope: movie identification and details inside the existing Entities views. This page specifies implementation; it does not enable live provider calls. TV-show integration remains Phase 8.

1 · Experience

Reuse the compact Entities table, board and detail views. Search suggestions distinguish movies by title, release year and poster. The user selects a result; never bind a movie merely because its title matches.

Approved detail fields: canonical title, release date/year, poster, expandable synopsis, runtime, genres and IMDb link. Missing fields are omitted. Trailers, cast and extra artwork are outside the approved initial display scope.

Keep existing To be seen / Seen statuses and repeat completion history. Catalog refresh must never alter viewing status, completion events, creation time or article associations. Identified titles follow catalog metadata; the owner edits a separate alias. Manual movies remain supported when search fails.

IMDb rating is not included: TheTVDB score is a popularity signal, not an IMDb rating. A separate ratings source requires its own decision.

MovieCatalogProvider exposes search(query, language, page) and getMovie(externalId, language). Results use neutral records: CatalogMovie, CatalogCandidate, CatalogPage and ExternalMovieReference(provider, externalId). Provider DTOs, bearer tokens, endpoints and error payloads remain inside infrastructure.

The Entities application calls an exposed movies application interface. Clients receive stable Know catalog UUIDs, not provider-specific routes. Keep provider enums out of public client contracts; provider identifiers are extensible strings. MapStruct maps provider DTOs only inside the adapter. ArchUnit enforces boundaries.

Swap procedure: implement the port, register the adapter and change configured provider. Keep existing catalog UUIDs and references; attach new provider references through verified external identifiers or reviewed matches. Changing configuration alone cannot safely rematch an entire catalog.

Never fall back silently to a different provider. Preserve cached details during migration, background-rematch missing references, report ambiguous matches for review, and retain rollback configuration. Refresh applies only after a valid mapping exists. The adapter and its tests are the only provider-specific code.

4 · Provider-neutral API proposals

These are proposals for review, not approved production contracts. Export the final typed OpenAPI schema through springdoc and generate client types during builds.

OperationBehavior
GET /api/v1/movie-catalog/searchquery, language, cursor → candidates {catalogId, title, year, posterUrl}, nextCursor, stale flag. Opaque cursor hides provider paging.
GET /api/v1/movie-catalog/{catalogId}Neutral metadata plus attribution and freshness; no API key or provider DTO.
PUT /api/v1/entities/{id}/movie{entityVersion, catalogId} identifies an owned MOVIE entity; returns updated entity and mapping versions.
GET /api/v1/entities/{id}/movieCombined metadata, alias, status, versions and attribution. User history stays in existing completion endpoints.
PATCH /api/v1/entities/{id}/movie{version, alias} changes the optional alias; null clears it. Cannot overwrite canonical title.
POST /api/v1/entities/{id}/movie/change-match{entityVersion, version, catalogId, confirmed:true} explicitly corrects a match. Approved behavior: retain alias, status, history and article links.

Use existing authentication and ownership rules: missing/foreign records both 404, invalid requests 400, duplicate identity or stale version 409 with stable reasons. Provider failures return meaningful retryable errors and must not masquerade as no search results. Search/catalog endpoints use existing authenticated access.

5 · Fast, economical, resilient

Approved configurable defaults: search after 2 characters; debounce 300 ms; show 8 suggestions initially. Cache successful searches 24 hours, empty results 15 minutes, movie details 7 days. Serve stale metadata on transient failure for up to 30 days and refresh in the background. All cache durations are configurable through application.yml.

Persist cache entries in PostgreSQL so they survive restarts. Deduplicate concurrent misses across pods with expiring leases; do not hold a database transaction during HTTP calls. Ignore outdated autocomplete responses. Bound response sizes, HTTP timeouts and worker concurrency; configure a provider-specific request budget from the granted license.

Respect HTTP 429 Retry-After; share cooldown across pods. Use bounded configurable backoff for transient failures, surface failures after retries, and preserve existing metadata. Provider authentication is server-side: obtain and renew the bearer token using the project API key, never expose either credential to clients.

Startup: no login, cache warm-up, catalog download or metadata refresh on the startup critical path. Initialize on demand/background; keep the existing under-5-second save-ready target. Test provider outages and expired tokens.

6 · License & attribution

TheTVDB publishes a free tier below $50,000 annual company revenue, with attribution; parent-company revenue counts. Register Know and obtain the appropriate project key. Confirm applicable terms during enrollment. Do not use a subscriber-supported key that requires each user to subscribe unless explicitly selected.

Display compact linked attribution where metadata is viewed unless the provider approves another arrangement: Source: TheTVDB The neutral API returns attribution text/link so another adapter can supply its own requirements. A provider setting cannot remove attribution obligations. Artwork rights remain subject to applicable terms.

7 · Implementation checkpoints

  1. Review: display fields, explicit result selection, locked canonical title with editable alias, preserved user data on match correction and cache defaults are approved. Finalize the remaining API contracts, typed schema and migrations. Pause for review.
  2. Backend: neutral port, TheTVDB adapter, persistent cache, owner mapping, version checks and OpenAPI. Unit tests and full HTTP-to-PostgreSQL integration tests with a stub provider. Pause for review.
  3. Webapp: autocomplete and compact movie details in Entities; alias, manual fallback, visible attribution, error/loading/stale states. Responsive desktop/mobile verification. Pause for review.
  4. Swap verification: test a second fake provider adapter, retained UUIDs, remapping, ambiguous identities and rollback. Optional live smoke test with a supplied key. Pause for acceptance.

Required tests: unit classes end Test; full-flow integration classes end IT and reuse application context. Use JUnit, AssertJ, Testcontainers PostgreSQL and HTTP provider stubs. Never mock static methods. Verify search → select → identify → fetch → edit alias → complete → refresh without changing history; duplicate remakes, concurrent additions, stale versions, cross-account isolation, 429 cooldown, restart-safe cache/jobs and malicious synopsis sanitization.

Use ArchUnit to prohibit provider-specific imports in application/presentation. Frontend Vitest and React Testing Library cover interactions, keyboard selection and stale response suppression. Run required build/lint/type checks, verify schema drift and report evidence. Do not call live APIs from routine automated tests.
