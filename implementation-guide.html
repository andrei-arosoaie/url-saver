3 · Rules for the implementing agent

  • Ask whenever a required detail is unclear. Explain options and consequences concisely; use selectable questions in batches of five when practical. Do not turn an unanswered question into approval.
  • Make changes visible. New phases and pages must appear in the shared top navigation on every page. Phase 1 is Functionality; Phase 2 is Timeline & Entities; Phase 6 is Automatic Identification; Phase 7 is Article Connections; Phase 9 is Authentication & Authorization. Link directly to new schema, contracts and implementation details; do not bury them in another phase.
  • Record each answer in its relevant page and this guide. Remove obsolete alternatives and keep the latest state.
  • Build unit tests and complete-flow integration tests. Integration tests exercise HTTP endpoints → real application services → transactions → real PostgreSQL with Flyway, verifying responses and persisted results. Cover save → read/list, enrichment, duplicate → explicit update, version conflicts and ownership isolation, including failures. Repository tests support this coverage; they never replace complete flows. Until security is implemented, mock authentication only in automated tests; afterwards verify real security flows. Integration class names end with IT; unit class names end with Test. Reuse the shared BackendIntegrationSupport Spring context and PostgreSQL container across backend ITs; reset fixtures between tests without restarting the context.
  • Verify every change. Run relevant checks, inspect actual results, fix failures, and rerun the affected checks. Report unrun or blocked checks honestly.
  • Keep the architecture: com.know; package by feature; presentation → application ← infrastructure; no cross-feature cycles; ArchUnit enforcement.
  • API and application DTOs are separate Java records; JPA entities stay in infrastructure. Spring-managed MapStruct at both boundaries. Lombok constructor injection only.
  • No lazy loading in controllers. Explicit Spring Data JPA queries/Specifications; application transactions; OSIV disabled; Flyway migrations and Hibernate validation.
  • Use compatible stable releases, Spring BOM versions where managed and explicit versions otherwise. Verify the full toolchain instead of copying historical version examples from these pages.
  • Preserve existing work. Do not publish, deploy, create external accounts, or configure paid resources without the applicable user authorization.

6 · Done means verified

  • Backend: compile, unit/integration tests, ArchUnit, Spotless, migrations and schema validation pass.
  • Extension: npm ci, ESLint, Prettier, TypeScript checks, Vitest/RTL and production Firefox build pass.
  • Contract: backend CI fails on drift from committed OpenAPI YAML. Shared schema changes trigger extension checks; generated TS files are build outputs, not committed sources.
  • Webpage: selected stack build/checks pass; inspect actual desktop/mobile interaction, including error and link-only states. State any unavailable device/browser verification.
  • Startup: benchmark under deployment-like limits. Target under five seconds from process start to save-ready, excluding Render wake-up; no extra first-save warm-up. Record environment, timings, repetitions and first-save latency. Liveness alone is insufficient.
  • Handoff: list changed behavior, commands run, results, unresolved issues and deferred checks. Claim completion only when required checks pass or the user explicitly accepts a documented limitation.
